## Major

#### ConfirmedViewModel launches an unguarded fetchOne — any transport failure crashes the app
`app/src/main/java/in/artistant/app/feature/booking/ConfirmedScreen.kt:71` — error-handling · booking

ConfirmedViewModel.init calls `bookingsRepository.fetchOne(bookingId)` inside `viewModelScope.launch` with no try/catch. SupabaseBookingsRepository.fetchOne (BookingsRepository.kt:159-172) wraps EVERY Throwable in `BookingRepositoryError.Underlying` and rethrows — it never returns null on failure, only on a genuine zero-row result. viewModelScope is `SupervisorJob() + Dispatchers.Main.immediate` with no CoroutineExceptionHandler, so the exception escapes to the thread's uncaught handler and kills the process. Failure scenario: client taps 'Send request', the booking lands, ConfirmedScreen opens, the device drops connectivity (or PostgREST 5xx) during this single read → app crashes on the screen that exists to reassure the client their request went through, with the booking already created server-side. Every sibling ViewModel guards this exact call: BookingDetailViewModel.kt:61 wraps it in `runCatching{}.getOrNull()`. FakeBookingsRepository.fetchOne never throws, so no unit test can catch this. Also note `isLoading` is set in this same update and never read by ConfirmedScreen.

```
init { viewModelScope.launch { val booking = bookingsRepository.fetchOne(bookingId) ... } }
```

**Fix:** Wrap in runCatching (mirroring BookingDetailViewModel.refresh) and surface a load-failure state; or catch BookingRepositoryError and render a retry.

**Verifier:** Mechanism verified end to end. ConfirmedScreen.kt:69-81 launches with no try/catch; SupabaseBookingsRepository.fetchOne (BookingsRepository.kt:159-172) rethrows every Throwable as BookingRepositoryError.Underlying and returns null only on a genuine zero-row read; viewModelScope is SupervisorJob()+Main.immediate with no CoroutineExceptionHandler, and nothing in the app installs an uncaught handler (SentryCrash.kt:13 says the SDK is not even linked). Every other throwing repo call in a viewModelScope guards: BookingDetailViewModel.kt:61, BookingsViewModel.kt:47-63 (try/catch), ArtistGigsViewModel.kt:46-62, ArtistListViewModel.kt:56-58, MessagesViewModel.kt:209/212 — ConfirmedViewModel is the lone outlier. isLoading is indeed written and never read. Downgraded from critical: it is a crash on a transport failure during one read on a transient screen, not data loss or an unavoidable/launch crash.

#### Calendar event map is persisted into the DataStore that sign-out wipes, stranding mirrored gigs forever
`app/src/main/java/in/artistant/app/platform/calendar/CalendarSyncService.kt:250` — data-loss · platform-core

`CalendarSyncService.save()` writes its `PersistedState` (the bookingId -> calendar eventId map) via `prefs.setString(PREF_KEY, ...)` (line 250) and reads it back via `prefs.getString(PREF_KEY)` (line 131). Both hit `AppPreferences.dataStore` (`artistant.state`) — the exact store `AppPreferences.wipeAll()` clears (AppPreferences.kt:79-81), which `SessionManager.signOut()` calls (SessionManager.kt:242). AppPreferences deliberately declares a SEPARATE `calendarStore` (`artistant.calendar`, AppPreferences.kt:24) with `calendarState` / `setCalendarState` / `wipeCalendar` (lines 86-96) whose comment states the invariant: 'the map is the only handle to clean them up later, so a sign-out must keep both. Only delete-account (wipeCalendar) clears it.' That entire API has ZERO callers anywhere in app/src (verified by grep) — it is dead, and the invariant it documents is violated. Failure scenario: artist enables Sync gigs to calendar, 6 confirmed gigs get mirrored into CalendarContract, artist signs out. `wipeAll()` deletes the `calendarSync` key. The 6 events remain in the phone's calendar and the eventId map is gone, so `removeAllSyncedEvents()` (line 423) can never find them again — neither a later disable nor `wipeForAccountDelete()` can retract them. Secondary effect: the in-memory `persisted` is NOT reset by `clearSessionState()` (line 153), so the next `save()` after a different user signs in rewrites the previous account's event ids into the new user's blob.

```
CalendarSyncService.kt:250 `prefs.setString(PREF_KEY, json.encodeToString(persisted))` + AppPreferences.kt:79-81 `suspend fun wipeAll() { context.dataStore.edit { it.clear() } }` while AppPreferences.kt:89-91 `suspend fun setCalendarState(json: String) { context.calendarStore.edit { it[calendarStateKey] = json } }` has no callers
```

**Fix:** Point `CalendarSyncService.load()/save()` at `prefs.calendarState` / `prefs.setCalendarState(...)`, and have the delete-account path call `prefs.wipeCalendar()` (from `wipeForAccountDelete`). Also reset `persisted` in `clearSessionState()` so a second account never inherits the first account's map.

**Verifier:** CalendarSyncService.save()/load() (lines 250, 131) go through prefs.setString/getString, which hit AppPreferences.dataStore ('artistant.state') — the exact store wipeAll() clears (AppPreferences.kt:79-81), and SessionManager.signOut() calls prefs.wipeAll() (line 241) before pushService.onSignedOut(). The purpose-built calendarStore API (calendarState/setCalendarState/wipeCalendar, AppPreferences.kt:86-96) has zero callers repo-wide (grep: only its own declarations), so the invariant its comment states is violated. ProfileViewModel.signOut() (line 214) calls only clearSessionState(), which clears lastSeen and the reconcile job — it does not delete events and does not reset `persisted`, so the map is gone from disk while the CalendarContract events remain, and removeAllSyncedEvents() can never find them. The secondary claim also holds: `persisted` (incl. ownerUserId and map) survives sign-out in memory.

#### FCM token is never released on sign-out and never re-claimed on an in-process sign-in, so pushes follow the wrong account
`app/src/main/java/in/artistant/app/platform/push/PushService.kt:84` — push · platform-core

`onSignedOut()` only calls `tabRouter.clearTransients()`. The `device_tokens` row claimed for this device via the `claim_device_token` RPC (line 118) keeps `user_id` = the signed-out user. Worse, `SessionManager.signOut()` calls `prefs.wipeAll()` (SessionManager.kt:242), which deletes `LAST_FCM_TOKEN_KEY` (line 123), so the token can't even be unregistered afterwards. And `persistToken` is only reached from `registerOnLaunchIfPermitted()` — invoked exactly once, in `ArtistantApplication.onCreate` (ArtistantApplication.kt:20) — or from `registerAfterPermission()`, invoked only by the signup notification step (`NotifPermissionScreen.kt:55`). A returning user signing in does not pass through either. Failure scenario: user A signs in, token T is claimed for A. A signs out and user B signs in on the same device without the process being killed. Nothing re-runs `claim_device_token`, so T is still mapped to A: A's new-message and booking pushes are delivered to B's phone (a cross-account content leak), and B receives no pushes at all until the app is cold-started. `DeviceTokenRepository.unregister(fcmToken)` exists for precisely this (DeviceTokenRepository.kt:26) and is never called.

```
PushService.kt:83-85 `fun onSignedOut() { tabRouter.clearTransients() }` — no token delete, no re-registration hook on sign-in
```

**Fix:** Read `LAST_FCM_TOKEN_KEY` and issue a token delete (or a `claim_device_token` with a null user / a `device_tokens` delete) BEFORE `prefs.wipeAll()` runs, and call `registerOnLaunchIfPermitted()` from the authenticated branch of `SessionManager`'s session-status observer (or from `RootViewModel.routeSignedIn()`) so every sign-in re-claims the token.

**Verifier:** onSignedOut() (83-85) only calls tabRouter.clearTransients(); nothing deletes or re-claims the device_tokens row, and SessionManager.signOut() runs prefs.wipeAll() (241) which drops LAST_FCM_TOKEN_KEY (and runs after client.auth.signOut(), so a later delete would be unauthenticated anyway). Grep confirms persistToken is reachable only from registerOnLaunchIfPermitted (ArtistantApplication.onCreate, the sole call site) and registerAfterPermission (NotifPermissionScreen.kt:55, signup-only) — no sign-in path re-runs the claim, so a returning user signing in after an in-process sign-out leaves the token mapped to the prior account. DeviceTokenRepository.unregister exists and is never called. Latent until the operator wires google-services.json/send-push, but the defect is exactly as described and the consequence is cross-account push delivery.

#### The Auth step is a one-way trap: nothing advances past it unless the RootGate value itself changes
`app/src/main/java/in/artistant/app/feature/signup/SignupFlow.kt:64` — correctness · signup-ui

`LaunchedEffect(startStep, startMode) { viewModel.resumeAt(startStep, startMode) }` is the ONLY production mechanism that moves the flow off `SignupStep.Auth`. `SignupViewModel.onAuthCompleted()` (SignupViewModel.kt:181), which exists precisely to advance past Auth and clear the notice, has no production call site at all (grep: only SignupViewModelTest.kt:194). In the `RootGate.Onboarding` branch (ArtistantNavHost.kt:71-79) `startStep`/`startMode` are the literals `Profile`/`Signup`, so the effect's keys never change while that gate holds.

Reachable in the mainline: a brand-new user does Welcome → Role → Auth → sign in → gate flips NotSignedIn → Onboarding → resumeAt(Profile). They are now on ProfileScreen with a live session. ProfileScreen ships a visible back chevron (`onBack = viewModel::back`, ProfileScreen.kt:82) and SignupFlow.kt:80 also enables system back on Profile. `prevStep(Profile, Signup)` = `Auth`. The user is now on SignupAuthScreen with a live session and no forward control. Re-authenticating does not help: `SessionManager.completedSignIn()` bumps `signInGeneration`, `RootViewModel.routeSignedIn()` re-runs and assigns `_gate.value = RootGate.Onboarding` — an equal `data object`, so MutableStateFlow conflates it and never emits, the `when` branch never recomposes, and the LaunchedEffect keys are unchanged either way. SignupFlow.kt:80 also leaves system back disabled on Auth, so back exits the Activity. The only escape is killing the process.

Second, independent path into the same trap: `saveProfile`'s `AppError.NotFoundOrUnauthorized` branch (SignupViewModel.kt:239-248) deliberately parks the user on Auth with "Please sign in again to save your profile." `mapPostgrest` (core/result) produces that error from a PGRST116 RLS denial with a perfectly live session, so the bounce fires without the session ever dropping — and then nothing can advance. This branch has a passing unit test (SignupViewModelTest.kt:179) that asserts the trap is entered.

```
LaunchedEffect(startStep, startMode) { viewModel.resumeAt(startStep, startMode) }   // SignupFlow.kt:64
BackHandler(enabled = state.step == SignupStep.Role || state.step == SignupStep.Profile)  // :80
fun onAuthCompleted() = _state.update { ... }   // SignupViewModel.kt:181 — zero production callers
```

**Fix:** Wire the missing edge. Either (a) observe the session in SignupFlow/SignupAuthScreen and call `viewModel.onAuthCompleted()` when `SessionManager.sessionStatus` becomes Authenticated while `state.step == Auth`, or (b) make the gate authoritative — key the LaunchedEffect on the gate identity (or expose a monotonic `routingGeneration` from RootViewModel) so a same-value re-route still re-seeds the step. Also drop `Auth` from the set of steps `back()` can reach when a session is live.

**Verifier:** Every link in the chain checks out. `onAuthCompleted()` (SignupViewModel.kt:181) has zero production callers — grep over app/src returns only the declaration and SignupViewModelTest.kt:194. `LaunchedEffect(startStep, startMode)` (SignupFlow.kt:64) is keyed on literals (`Profile`/`Signup`, ArtistantNavHost.kt:72-73) inside the Onboarding branch, so it never re-fires while that gate holds. `RootGate.Onboarding` is a `data object` (ArtistantRoot.kt:20), so `_gate.value = RootGate.Onboarding` (RootViewModel.kt:102) is conflated by MutableStateFlow — a same-uuid re-auth bumps `signInGeneration`, re-runs `routeSignedIn`, and emits nothing, leaving the `when` branch and the LaunchedEffect untouched. ProfileScreen's chevron (ProfileScreen.kt:82 → `viewModel::back`) plus `prevStep(Profile, Signup) == Auth` (SignupStep.kt:21-24) puts a signed-in user on SignupAuthScreen with no forward control, and BackHandler is disabled there (SignupFlow.kt:80), so back finishes the Activity. Second entry confirmed too: `mapPostgrest` maps PGRST116 → NotFoundOrUnauthorized (AppError.kt:32), which saveProfile parks on Auth (SignupViewModel.kt:239-248) — the passing test at SignupViewModelTest.kt:179 asserts entry into the trap. Only mitigation: pressing back again finishes the Activity and a relaunch rebuilds the VM at Profile, so the escape is 'quit and reopen', not truly unrecoverable — still a dead-end screen in the mainline signup path.

#### Save & exit is tappable while the draft is still restoring and overwrites the saved draft with a blank one
`app/src/main/java/in/artistant/app/feature/wizard/WizardViewModel.kt:518` — data-loss · wizard

WizardScreen.kt:96-101 renders WizardTopBar (which owns 'Save & exit') whenever `step != Done` — it is NOT gated on `state.isRestoring`, unlike the body at WizardScreen.kt:109 which shows a spinner. saveAndExit() has no isRestoring guard either: it writes `_state.value.toDraft(ownerId)` immediately. During restore, `_state.value` is still the constructor default WizardUiState() — step=Identity, blank stageName/handle/category, no packages, coverFileName="", samples=[]. The restore window is not short: restore() awaits `users.fetchSelfProfile()` (WizardViewModel.kt:137), a network round trip with no timeout, and it is awaited unconditionally even when the draft already holds every field. Tap Save & exit in that window and the artist's entire saved draft (stage name, handle, pricing tiers, rider, bio, cover + sample refs) is replaced by a blank draft and the session is signed out. On sign-in, restore() reads the blank draft, and because the reference set is now empty the sweep at line 154 also DELETES the staged cover and audio files from disk. Unrecoverable.

```

        session.currentUserId?.lowercase()?.let { ownerId ->
            runCatching { draftStore.save(_state.value.toDraft(ownerId)) }   // _state.value is still WizardUiState() while isRestoring
```

**Fix:** Either hide/disable the Save & exit control while `state.isRestoring` (WizardScreen.kt:96), or make saveAndExit() a no-op-then-signout when `_state.value.isRestoring` — never write a draft assembled from the pre-restore default state.

**Verifier:** WizardScreen.kt:96 gates WizardTopBar (which owns Save & exit) on `state.step != WizardStep.Done` only — never on `state.isRestoring`, unlike the body at line 109. `saveAndExit()` (WizardViewModel.kt:518-525) writes `_state.value.toDraft(ownerId)` unconditionally, and WizardDraftStore.save (line 165) has no blank-draft guard. The restore window is genuinely unbounded: restore() awaits `users.fetchSelfProfile()` (line 137), which is two sequential Postgrest reads (UsersRepository.kt:92-116) with no timeout. The downstream damage is exactly as described — on the next sign-in the blank draft classifies as `Mine`, so the sweep at line 154 runs with an empty reference set and `mediaCache.delete` removes the staged cover and every audio file. Contrast with the deliberate `drop(1)` guard on the debounced writer (line 256 KDoc: 'so an immediate kill can't overwrite a good draft with a blank one before restore has landed') — the same hazard is left wide open on the one control that is visible during that window. Probability is the only mitigator; impact is total and unrecoverable.

#### Publish writes setup_complete before published, permanently stranding an artist whose publish partially fails
`app/src/main/java/in/artistant/app/feature/wizard/WizardViewModel.kt:555` — correctness · wizard

publish() is a 3-call non-atomic sequence: step 1 (`artists.publishWizardProfile`) writes `setup_complete = true` (ArtistsRepository.kt:203 `setupComplete = true` inside WizardPublishRow), and step 3 (`artists.setPublished`, line 566) writes `published = true`. If step 2 or 3 fails — dropped connection between round trips, which is the normal failure on Indian mobile data — the server ends up with setup_complete=true and published=false. RootViewModel.kt:157 gates wizard entry on `profile.artistSetupComplete != true`, so the next launch routes the artist to the artist tabs, not the wizard. `setPublished(published = true)` has exactly ONE call site in the whole app (this line 566), and EpkScreen.kt:172 only offers 'Finish your profile' → wizard when `state.artist == null && !state.setupComplete`, which is now false. …
artists.setPublished(userId, published = true)                        // separate call, 2 round trips later
```

**Fix:** Port the iOS fix: drop `setupComplete` from WizardPublishRow (ArtistsRepository.kt:203/627) and have `setPublished` PATCH `{published, setup_complete}` together, so the only write that marks setup finished is the one that makes the artist live.

**Verifier:** Every link in the chain checks out. ArtistsRepository.kt:203 sets `setupComplete = true` inside the WizardPublishRow upserted at step 1 (line 206), and `published` is flipped by a separate PATCH in `setPublished` (line 213-225) two round trips later (WizardViewModel.kt:555 vs 566). `setPublished` has exactly one call site in the app (verified by grep: only WizardViewModel.kt:566 + the Fake). No other in-app control writes `published`. The iOS citations are accurate verbatim: ArtistsRepository.swift documents 'Deliberately does NOT touch setup_complete' and `publish(_:)` PATCHes `Patch(published: true, setup_complete: true)` in one write. Not critical only because it needs a mid-sequence failure the artist then walks away from (a same-session retry recovers), but when it lands there is no in-app remedy at all.

#### Sample titles are derived from a SAF document URI's last path segment, which is an opaque document id — and the EPK offers no rename
`app/src/main/java/in/artistant/app/feature/epk/EpkScreen.kt:122` — correctness · epk

`ActivityResultContracts.OpenDocument()` returns a document URI such as `content://com.android.providers.media.documents/document/audio%3A1000000042`; `uri.lastPathSegment` is then `"audio:1000000042"`. `onSamplePicked` does `displayName?.substringBeforeLast('.')?.trim()?.ifBlank { null } ?: "Sample"` (EpkViewModel.kt:1101) — with no '.' in the string, `substringBeforeLast` returns the whole thing, so the title stored in `samples.title` and rendered on the artist's PUBLIC profile is `"audio:1000000042"`. if (uri != null) viewModel.onSamplePicked(uri, uri.lastPathSegment)
```

**Fix:** Resolve the real name before handing it over: query `contentResolver.query(uri, arrayOf(OpenableColumns.DISPLAY_NAME), …)` (off the main thread) and pass that, falling back to `"Sample"`.

**Verifier:** Verified: EpkScreen.kt:122 passes uri.lastPathSegment from ActivityResultContracts.OpenDocument(), which is a provider-defined document id ('audio:1000000042', 'primary:Music/song'), never a bare display name; onSamplePicked's substringBeforeLast('.') is a no-op on a string with no dot. #### Debounced saves treat coroutine cancellation as a write failure, so a second tap paints a false "couldn't save" banner
`app/src/main/java/in/artistant/app/feature/epk/EpkViewModel.kt:905` — error-handling · epk

Every persist path is launched into a Job that the NEXT edit cancels (`techSaveJob?.cancel()` at :894, `packagesSaveJob?.cancel()` at :843, `bioSaveJob` :667, `socialsSaveJob` :744, `promptsSaveJob` :547), and every one of them wraps the network call in `kotlin.runCatching`, which catches `Throwable` — including `CancellationException`. Concrete failure: the tech rider and package-remove paths schedule with `immediate = true`, i.e. no debounce delay, so `persistTech` is already inside `techRider.replaceAll(...)` when the artist taps a second preset chip ~200ms later. ## Refuted in verification

- **The calendar side effect sits inside create()'s failure boundary, so a local throw reports a booking that already landed as failed** (`…/data/repository/BookingsRepository.kt:119`) — The cited mechanism cannot occur. CalendarSyncService.ingest (platform/calendar/CalendarSyncService.kt:144-151) is `session.currentUserId` + `lastSeen[id] = b` + `hasWritePermission()` (ContextCompat.checkSelfPermission) + `scheduleReconcile()` (a scope.launch) — none of which throws. A ConcurrentModificationException is raised by the ITERATOR, i.e. inside reconcileNow()/busyDays()/clashes(), never by a `put` on the map, so it cannot propagate out of `ingest` and into create()'s catch. With no reachable throw, the described double-insert-on-retry path does not exist. The structural nit (a side effect inside the network try) is fair style but has no demonstrable failure here; the closer real hazard in that block is `decodeSingle<DbBooking>()` failing after the row committed, which is not what was claimed.
- **When the photo read fails the reorder controls vanish with no explanation, unlike every other gated section on the screen** (`…/feature/epk/EpkScreen.kt:797`) — The described state is unreachable. state.photos is assigned in exactly two places: loadMedia's onSuccess, which sets photos and photosHydrated = true in the same copy (:361), and movePhoto, which is gated on photosHydrated (:1067). photosHydrated is never reset to false. Therefore photos.isNotEmpty() implies canReorder == true — and PhotoActionRow only composes when photos is non-empty and a tile is selected (:712). A failed photo read leaves photos empty, so PhotosSection renders its empty-state copy and no grid, no action row, no missing buttons. The 'artist sees the reorder affordances simply not exist' scenario cannot occur, and the suggested explanatory note would be dead copy for the same reason.
- **Camera capture writes into the WizardMediaCache directory instead of the declared wizard-capture staging dir, and is never deleted** (`…/feature/wizard/WizardMediaSteps.kt:197`) — The central claim is contradicted by the file the auditor cites. res/xml/file_paths.xml's FIRST entry is `<cache-path name="wizard" path="artist-wizard/" />` with the comment 'WizardMediaCache + TakePicture staging under cacheDir/artist-wizard' — i.e. the directory WizardMediaSteps.kt:197 writes into is explicitly declared for TakePicture staging, and the FileProvider grant resolves through it. The unused `wizard-capture` entry reads as merge residue (the two comments are prefixed 'Ours:' and 'Main:'). The 'never deleted' half is also handled elsewhere: because the capture lands inside `artist-wizard/`, `stagedFileNames()` enumerates it and sweepOrphanMedia (WizardViewModel.kt:190-207) deletes it as an orphan on the next restore — the proposed fix of moving it to `wizard-capture/` would put it outside the swept directory and make the leak permanent. What survives is a duplicate JPEG in an OS-reclaimable cacheDir alongside the staged originals nothing deletes post-upload either, plus a duplicated directory literal: trivial.
- **Unknown gig-request status decodes to Open — the one status that hands the artist Accept/Decline/Counter** (`…/data/model/GigRequest.kt:27`) — The cited behavior cannot occur against this backend, and the parity framing is backwards. `gig_requests.status` is a Postgres ENUM `public.gig_request_status` created in 0001_initial_schema.sql:246 with exactly ('open','countered','accepted','declined','expired') — all five are mapped in GigRequestStatus — and no migration anywhere adds a value (`grep 'add value'` over the migration set returns nothing); the column is NOT NULL with a default, and RequestsRepository selects `*`, so `raw` cannot be null or unrecognised. Additionally iOS itself does `GigRequestStatus(rawValue: status) ?? .open` (RequestsRepository.swift:409), so Android is a faithful port, not a parity gap — the BookingStatus `Unknown` case exists because bookings have a richer, evolving lifecycle. Legitimate forward-compat hardening if the enum ever grows, but not a live defect.
- **Raw hex cover-gradient palettes live in the data model, outside the token system** (`…/data/model/Artist.kt:122`) — The two arithmetic sub-claims are true (0xFF7C5CFF == AppColors.accent; 0xFF0F1014 != AppColors.bg 0xFF0A0A0A) but the stated defect is not. The hero does not dissolve via the palette's terminal stop — Hero paints the gradient/cover and then a SEPARATE scrim `verticalGradient(1f - heroFade to Transparent, 1f to colors.bg)` (ArtistProfileScreen.kt ~295-303), with a KDoc explaining precisely that the dissolve must end on bg. The 0F1014 stop is a deliberate dark floor for the name/price strip on tiles, documented as such in the source of truth (ios-swift Models/ArtistGradient.swift:23), and the Android palette is a byte-for-byte port of that file — same six palettes, same placement in Models/data model. Re-litigating a deliberate iOS-parity port whose consequence claim does not hold.
- **The signup hero's radial gradients are positioned and sized in raw pixels, so they land differently on every density** (`…/feature/signup/WelcomeScreen.kt:76`) — The API claim is right — Brush.radialGradient's center and radius are pixels, and the arithmetic (300px = 27.8% of 1080 with a 233dp radius at 3x vs 41.7% with 350dp at 2x) is correct. But the described behaviour cannot occur, because neither glow is painted at all. L69-87 is `Box(Modifier.fillMaxWidth().heightIn(max = 420.dp).background(...).background(...))` with no trailing lambda, which resolves to Compose's CONTENT-LESS Box overload (EmptyBoxMeasurePolicy = layout(constraints.minWidth, constraints.minHeight)). The parent Box passes min constraints of 0, fillMaxWidth fixes only the width, and heightIn(max = ...) caps maxHeight while leaving minHeight at 0 — so the node measures screenWidth x 0dp and Modifier.background draws a zero-height rect. The two-tone radial hero is invisible on every device, at every density, so there is no drift to observe. The real defect on these lines is the missing height (e.g. .height(420.dp) or .fillMaxHeight(fraction)), and the raw-px offsets only become a live problem once that is fixed.
- **DateScroller pins "today" in an unkeyed remember, so a screen left open across midnight shows a stale strip** (`…/designsystem/component/DateScroller.kt:60`) — The remember is unkeyed as quoted (60-61), but the stated impact cannot happen: `DateScroller(` has no call site anywhere in app/src — grep across main and test returns only the declaration itself plus two prose mentions (BookingSlots.kt:19 and DateChipLinesTest.kt:18 cite iOS DateScroller.swift for parity, they do not use it). No booking screen renders this component, so nothing "keeps offering yesterday" and isFree never evaluates anything. It is also the only `remember { LocalDate.now() }` in the codebase, so there is no sibling instance to inherit the claim. This is dead design-system code — the same verdict the auditor reached for AmbientRoleWash two findings later, applied inconsistently here.
- **theStoreReportsItselfInactive compares a property to its own definition** (`test:…/feature/paywall/EntitlementGateTest.kt:41`) — The central claim — 'cannot fail' — is wrong. The right-hand side is production code: EntitlementStore.subscriptionsActive (EntitlementStore.kt:32) currently delegates to AppEnvironment.subscriptionsEnabled, and the assertion's kill-set is exactly the mutation that matters here (hardcode `true`, or read a different flag), which is how a paywall would appear in front of a v1 booking. That is a delegation invariant, not assertEquals(x, x). The proposed replacement `assertFalse(store.subscriptionsActive)` has the same kill-set for that mutation and merely adds a tripwire on the planned operator flip — a design preference, and the flag's value is already pinned separately by subscriptionsAreOffInThisBuild. The secondary claim is also inaccurate: `assertFalse(store.isEntitled.value)` (the StateFlow) is not what nobodyIsEntitledWhileTheFlagIsOff asserts (it calls the isEntitled(productId) function). At worst this is mild redundancy.
